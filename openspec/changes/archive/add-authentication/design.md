## Context

交易系统目前是一个基于Reflex框架的量化炒股分析Web应用，使用Python作为前后端一体化开发语言，DuckDB作为数据库。系统当前没有用户认证功能，所有功能都是公开访问的。

为了保护用户数据和个性化功能，需要添加完整的用户认证系统。系统需要支持用户注册、登录、登出和密码重置等核心功能。

**约束条件**：
- 必须使用Reflex框架实现前后端一体化
- 数据库使用DuckDB
- 单功能初始代码量≤300行
- 所有产出物必须用简体中文撰写

**利益相关者**：
- 系统用户：需要安全的认证体验
- 开发团队：需要易于维护和扩展的代码结构

## Goals / Non-Goals

**Goals:**

1. 设计一个安全、可靠的用户认证系统架构
2. 定义清晰的认证流程和数据模型
3. 确保系统符合项目的技术栈约束和开发规范
4. 提供可扩展的设计，为未来功能（如权限管理）预留空间

**Non-Goals:**

- 不设计OAuth或第三方登录集成
- 不设计多因素认证（MFA）
- 不设计用户权限/角色管理系统
- 不设计用户个人资料管理功能

## Decisions

### 1. 认证机制选择

**决策**：使用Reflex内置的会话管理

**理由**：
- Reflex框架提供了内置的会话管理机制，无需额外实现
- 减少了自定义会话管理的复杂性和潜在的安全风险
- 与Reflex的状态管理系统无缝集成
- 符合项目"前后端一体化均为Python实现"的要求

**替代方案考虑**：
- JWT Token：需要额外的token管理和刷新逻辑，增加复杂度
- 自定义Session表：需要自行实现会话过期、清理等机制

### 2. 密码加密方案

**决策**：使用bcrypt加密，salt rounds设置为10

**理由**：
- bcrypt是业界标准的密码哈希算法
- 自带salt机制，防止彩虹表攻击
- 计算成本可调，salt rounds=10在安全性和性能之间取得平衡
- Python的bcrypt库成熟稳定，易于使用

**替代方案考虑**：
- Argon2：更安全但计算成本更高，可能影响性能
- PBKDF2：较老的标准，安全性略低于bcrypt

### 3. 数据库设计

**决策**：创建users表和password_reset_tokens表

**理由**：
- users表存储用户基本信息，使用UUID作为主键避免暴露用户数量
- password_reset_tokens表独立存储密码重置token，便于管理和清理
- 使用外键约束确保数据一致性
- 创建索引提升查询性能

**替代方案考虑**：
- 单表存储所有信息：会导致表结构复杂，查询效率降低
- 使用自增ID：会暴露用户数量，存在安全隐患

### 4. 认证状态管理

**决策**：创建AuthState基类，使用Reflex的State管理

**理由**：
- Reflex的State机制天然支持前后端状态同步
- 可以轻松实现认证状态的实时更新
- 便于在多个组件中共享认证状态
- 符合Reflex框架的最佳实践

**替代方案考虑**：
- 全局变量：不安全，且无法实现状态同步
- LocalStorage：仅前端存储，后端无法访问

### 5. 路由保护机制

**决策**：创建require_auth装饰器保护需要认证的页面

**理由**：
- 装饰器模式简洁易用，代码可读性高
- 可以灵活应用于任意页面或组件
- 便于统一管理认证逻辑
- 符合Python的编程习惯

**替代方案考虑**：
- 在每个页面中手动检查：代码重复，容易遗漏
- 中间件：Reflex框架不支持传统意义的中间件

### 6. Token生成方案

**决策**：使用Python的secrets模块生成安全token

**理由**：
- secrets模块专门用于生成加密安全的随机数
- 内置模块，无需额外依赖
- 比random模块更安全
- 适用于密码重置token等场景

**替代方案考虑**：
- uuid.uuid4()：虽然安全，但不是专门为安全token设计
- random模块：不安全，不应用于安全相关的场景

## Risks / Trade-offs

### 风险1：DuckDB的并发支持有限

**风险描述**：DuckDB主要用于OLAP场景，对高并发写入的支持可能不如传统的关系型数据库。

**缓解措施**：
- 用户认证操作的并发量通常不高，DuckDB足够应对
- 未来如果遇到性能问题，可以考虑迁移到PostgreSQL
- 在当前阶段，DuckDB的简单性和易用性更重要

### 风险2：Reflex会话管理的安全性

**风险描述**：依赖Reflex内置的会话管理，可能存在未知的安全漏洞。

**缓解措施**：
- 密码仍然使用bcrypt加密，即使会话被劫持也不会泄露密码
- 实施rate limiting防止暴力破解
- 强制HTTPS确保传输安全
- 定期更新Reflex版本以获取安全修复

### 风险3：密码重置token的安全性

**风险描述**：如果密码重置token泄露，攻击者可以重置用户密码。

**缓解措施**：
- Token使用secrets模块生成，具有足够的熵值
- Token设置过期时间（建议1小时）
- Token使用后立即标记为已使用
- 通过邮件发送token，确保只有邮箱所有者能收到

### 风险4：代码量超出300行限制

**风险描述**：认证系统功能较多，可能超出单功能初始代码量≤300行的规范。

**缓解措施**：
- 严格按照proposal中的代码量估算执行
- 优先实现核心功能（注册、登录、登出）
- 密码重置功能可以作为后续优化
- 如果必须超出，需要有性能数据支持

### 权衡1：安全性与用户体验

**权衡描述**：更强的安全性（如更复杂的密码要求）可能降低用户体验。

**权衡决策**：
- 当前阶段平衡两者：要求至少8位密码，包含字母和数字
- 未来可以根据用户反馈调整密码策略

### 权衡2：功能完整性与代码简洁性

**权衡描述**：添加更多功能（如记住登录状态）会增加代码复杂度。

**权衡决策**：
- 当前阶段保持简洁，只实现核心功能
- 未来可以根据需求迭代添加

## Migration Plan

### 部署步骤

1. **数据库迁移**
   - 执行SQL脚本创建users表和password_reset_tokens表
   - 验证表结构和索引创建成功

2. **代码部署**
   - 添加认证相关的Python包依赖（bcrypt、email-validator）
   - 部署认证State和事件处理函数
   - 部署前端认证页面组件
   - 更新路由配置，添加认证保护

3. **配置更新**
   - 配置SMTP服务用于发送密码重置邮件
   - 配置HTTPS证书（生产环境）
   - 配置rate limiting参数

4. **测试验证**
   - 执行单元测试、集成测试和安全测试
   - 验证所有认证流程正常工作
   - 验证安全措施有效

### 回滚策略

1. 如果发现严重问题，可以：
   - 回滚代码到之前的版本
   - 保留数据库表（不影响现有功能）
   - 禁用认证功能，恢复公开访问

2. 数据备份：
   - 部署前备份DuckDB数据库文件
   - 确保可以快速恢复到部署前的状态

## Open Questions

1. **SMTP服务选择**：目前尚未确定使用哪个SMTP服务发送密码重置邮件。需要评估成本、可靠性和易用性。

2. **密码策略细节**：具体的密码强度要求（如是否需要特殊字符、最大长度等）需要进一步讨论。

3. **Rate limiting实现**：Reflex框架下如何实现rate limiting需要调研，可能需要使用第三方库或自定义实现。

4. **密码重置邮件模板**：密码重置邮件的具体内容和格式需要设计，确保用户体验良好。

5. **错误处理策略**：各种错误场景（如用户不存在、密码错误、邮箱格式错误等）的具体错误提示需要统一设计。
